### B-1 (closed) — the phase-1 revision handshake was broken by phase 2

`updateDoc()` (`server.js:697-704`) moves the workspace revision, but the three phase-2 endpoints
that edit the document (`PATCH`/`DELETE …/members/:userId`, `POST …/plan`) did not report it, and
`src/core/api.js` only refreshed `api.revision` in `loadWorkspace` and `putWorkspace`. The next
write went out with a stale revision, was rejected with `409 {error:'Workspace changed elsewhere'}`,
and `store.js:114` set `S.ui.conflict = true` — after which every later save short-circuits. The
owner saw a "Created project" toast for a project the server never stored; the only recovery was a
full reload, which discarded every unsaved change.

It was invisible to the suite because no test ever changed a role or the plan and then kept editing
in the same session.

**Fix:** `server.js` returns the new revision from the three endpoints (`wsRevision()` helper);
`src/core/api.js` adopts it through `adoptRevision()` in `setMember`, `removeMember` and `setPlan`.
**Proof:** `test/membership.test.mjs` (a role change, a plan change and a member removal report the
revision, and the next write is accepted with it), `test/revision.test.mjs` (the client follows it),
and a Chromium test that changes a role in the Members page, creates a project and reloads to prove
the server stored it. All three fail without the fix.

### W-01 (closed) — accepting an invite invalidated every other session

`addMembership()` wrote the workspace document, and with it the revision, when someone accepted an
invite. The join happens in *another* session, so the inviter's browser could not be told the new
revision: its next write carried a stale one, was rejected with `409` and was dropped. The same
defect family as B-1, on a path where reporting the revision is not enough.

**Fix:** the membership row is the only thing a join writes now — `addMembership()` no longer
touches the document — and the roster is repaired on read: `syncProfiles()` adds the profile of
any member that has none, using the membership row as the source of truth. A stale document can
no longer drop a member either, because `docFromClient()` re-adds the stored profiles an incoming
document omits. Member ids are now assigned from the membership table, so a profile that is
repaired later still carries the id the row recorded.

**Proof:** `test/invite-revision.test.mjs` (the revision does not move, the roster is complete for
the inviter and for the joiner, and the inviter's next write is accepted) and a Chromium test that
lets an account join from another session while the owner's browser is open, then creates a project
and reloads. Both fail without the fix.

### W-01 variant (closed) — a restart moved the revision too

The boot-time backfill (`backfillMemberships()`) repairs server-owned state — the legacy profile
links and the demo switcher — and wrote the document back with a revision bump. A session that was
open across the restart therefore held a stale revision and lost its next write, the same symptom.

**Fix:** the repair is written without moving the revision. A restart is not an edit, and a client
cannot be told about it.

**Proof:** the second test in `test/invite-revision.test.mjs` reboots the real server on the same
`DATA_DIR` and asserts that the revision did not move, that a write crossing the restart is
accepted, and that the roster is still complete.

## Verdict

**tech_debt.** Every milestone requirement is satisfied and every phase is verified against the
codebase. The audit found three defects in the same family — the revision handshake between the
phase-1 concurrency control and the document-mutating endpoints (B-1), the same problem on the
invite-accept path, where the join happens in another session (W-01), and the same problem on the
boot-time repair, where a restart moved the revision once (W-01 variant). All three are closed,
with server, client and browser proof, and CI is green on the fix commit. What remains is deferred
hardening and a set of UI flows that are still unproven by an automated test.

The milestone is ready to archive. `/gsd-complete-milestone v1.1` is the next step.
