# G-44-3 — Diagnosis

## Symptom

Truth: "Every stored tz value reaches members[*].tz only through the resolveTz funnel — including the admin doc-PUT path (WR-01); a stored valid tz always preselects itself in the combobox (WR-02)."

- **WR-01 (write side):** an admin PUT with an arbitrary/hostile `tz` on *another* member's profile persists it verbatim. Only the requester's own tz passes through the resolveTz funnel. No live breakage (all reads funnel), but D-10's "never arbitrary strings stored in the doc" invariant is broken on the write side.
- **WR-02 (read/UI side):** a stored tz that is valid but non-canonical (`US/Pacific`, `america/new_york`, `UTC`) schedules correctly but does not match the combobox list, so `tzPreselect` shows **Europe/Paris** and one save silently rewrites the member's tz to Paris. Violates SC-4 "degrade without loss".

bug_class: Bohrbug (both fully deterministic, trivially reproducible).

## Root cause WR-01 — server.js admin doc-PUT path

`docFromClient` (server.js ~1674) → admin branch (~1697–1706):

```js
next.data.members = incomingMembers
  .map(m => {
    if (!m?.userId) return m;                      // doc-only members pass through WHOLLY
    const prev = official.get(m.userId);
    return prev ? { ...m, id: prev.id, userId: prev.userId, email: prev.email, role: prev.role, status: prev.status } : null;
  })
  .filter(Boolean);
```

The spread `{ ...m }` copies every property — including `tz` — verbatim from the untrusted incoming array. Only five access fields are pinned; `tz` is not among them. The resolveTz funnel is applied **only** in the self-carve-out block (~1716–1726), gated on `m?.id === membership?.member_id`:

```js
if (storedSelf) storedSelf.tz = (typeof incomingSelfTz === 'string' && incomingSelfTz.trim() === '') ? '' : resolveTz(incomingSelfTz);
```

The "never stored raw" comment above the carve-out is therefore false for any member other than self on the admin path — and wholly false for doc-only members (`return m` bypasses even field pinning).

Test gap: `test/settings-tz.test.mjs:168-184` ("admin PUT keeps the pinned-field block intact") exercises only a *valid* `Asia/Tokyo`, so the hole is invisible to the suite.

## Root cause WR-02 — tz.js returns raw input; preselect exact-matches a canonical list

`resolveTz` (tz.js:25-37): on successful Intl validation it `return v;` — the **trimmed input as-is**. Intl's constructor accepts aliases and case-insensitive input, so:

- `resolveTz('US/Pacific')` → `'US/Pacific'` (not `America/Los_Angeles`)
- `resolveTz('america/new_york')` → `'america/new_york'`
- `resolveTz('UTC')` → `'UTC'`

This "aliases accepted as-is" behavior is pinned by A2 in `test/tz-resolve.test.mjs:43-48` — the bug is spec'd into the test.

`tzPreselect` (src/pages/settings.js:159-172):

```js
const zone = resolveTz(s);
return TIMEZONES.some(z => z.id === zone) ? zone : 'Europe/Paris';
```

`TIMEZONES` (src/lib/timezones.js) is generated from `Intl.supportedValuesOf('timeZone')` (D-03: build-time only, gen-timezones.mjs:23), which contains **canonical ids only** — no links/aliases. So `US/Pacific` / case variants miss the list → Paris preselect → next save persists Paris. Note this is broader than aliases: `UTC` is *also* absent from `supportedValuesOf` (verified: `Intl.supportedValuesOf('timeZone').includes('UTC') === false`), so even the canonical string `UTC` preselects Paris today.

## Proposed fix routes

### WR-01 — funnel-validate every incoming member tz on the admin path (D-10)

In the admin-branch `.map()`, normalize `tz` the same way the carve-out does, preserving the `''` clears-to-empty semantics (D-07):

```js
return prev ? {
  ...m,
  id: prev.id, userId: prev.userId, email: prev.email, role: prev.role, status: prev.status,
  tz: m.tz === undefined ? prev.tz
    : (typeof m.tz === 'string' && m.tz.trim() === '') ? ''
    : resolveTz(m.tz),
} : null;
```

And for doc-only members (`!m?.userId`): return `{ ...m, tz: (typeof m.tz === 'string' && m.tz.trim() === '') ? '' : resolveTz(m.tz) }` (or strip `tz` entirely — decide with the D-10 owner; funneling keeps more admin capability, stripping is stricter).

Alternatively the review's stricter route: strip `tz` from all non-self incoming members so only the carve-out can ever write tz — but that removes the admin's legitimate ability to edit another member's tz through the doc, which the existing Asia/Tokyo test pins as expected behavior. **Funneling is the recommended route**: it keeps that capability and restores the single-choke-point invariant (D-07: "the funnel is the only validator").

With WR-02's canonicalization (below), the admin path then stores canonical ids too, tightening the byte-identical claim-key story.

### WR-02 — canonicalize at the funnel (server- and client-side, no D-03 violation)

In `resolveTz`, replace `return v;` with the Intl-resolved canonical id:

```js
try {
  const fmt = new Intl.DateTimeFormat('en-CA', { timeZone: v });
  return fmt.resolvedOptions().timeZone || v;
} catch { /* fall through to Paris */ }
```

**D-03 check:** `Intl.supportedValuesOf('timeZone')` stays build-time-only (gen-timezones.mjs). `resolvedOptions().timeZone` is *not* enumeration — it resolves a single already-named zone (alias/case → canonical IANA id, verified: `US/Pacific` → `America/Los_Angeles`, `america/new_york` → `America/New_York`). tz.js is a shared isomorphic module imported by both server and client; the canonicalization is therefore uniform on both sides and no build-time committed map is needed. **No D-03 conflict.**

Side effect: every stored tz (including legacy-label mappings and new writes) becomes a canonical id, so `tzPreselect`'s exact match against `TIMEZONES` succeeds for every valid stored value — the preselect fix falls out of the funnel fix with zero UI change.

**Residual `UTC` gap:** `resolvedOptions().timeZone` for `'UTC'` returns `'UTC'`, which is still absent from the generated list. Either (a) add `UTC` (and ideally the `Etc/GMT±n` family, if desired) to `gen-timezones.mjs` output as a small build-time supplement, or (b) accept that `UTC` preselects Paris (document it). Recommend (a) for `UTC` at minimum — it is the single most likely hand-typed non-list value. With route (a), tzPreselect needs no change at all.

### Test updates required by the funnel change (A2)

`test/tz-resolve.test.mjs:43-48` A2 pins `resolveTz('US/Pacific') === 'US/Pacific'`. The pin must be updated to `=== 'America/Los_Angeles'` and a case-variant assertion added (`'america/new_york'` → `'America/New_York'`). This is a deliberate decision-change to A2 (aliases still *accepted*, but *stored canonical*) and should be called out in the phase notes, not slipped in.

## Risks / interactions

1. **A2 decision change:** alias acceptance semantics change from "stored as-submitted" to "stored canonical". Reviewer-visible; update the A2 note in 44-CONTEXT if locked wording exists.
2. **Legacy stored aliases:** docs that already store `US/Pacific` (e.g. via the WR-01 hole) are never rewritten at rest (D-05: no migration outside a user save) — but reads/preselect now resolve them canonically, so the next self-save rewrites them to `America/Los_Angeles`. That is a behavior change on first re-save; harmless but observable.
3. **Byte-identical claim keys:** reminder keys are `ws:id:offset:due` — offset is computed from the *resolved* zone, and aliases resolve to the same instants as their canonical target, so existing claims remain valid across the canonicalization change. Digest keys (`ws:user:digest:localDate`) derive `localDate` from the resolved zone — same-zone aliases produce identical dates; no claim invalidation. Verified reasoning, but add a dedup test saving `US/Pacific` then `America/Los_Angeles` should NOT be needed since both resolve identically — one assertion that `localParts` output is unchanged for alias input vs canonical is enough.
4. **`''` semantics preserved:** the `tz === undefined → prev.tz` guard in the WR-01 fix matters — without it, an admin snapshot that omits a member's tz would wipe it. Same distinction must be made for doc-only members. Non-string `tz: null` still coerces to Paris (IN-02, out of scope here — same fix shape could cover it cheaply: treat non-strings as absence).
5. **`UTC` not in list:** canonicalization alone does not fix `UTC` preselect; without the generator supplement, `UTC` (a realistic user entry) still preselects Paris and a save rewrites it to Paris. Decide explicitly.
6. **ICU variance:** `resolvedOptions().timeZone` canonical targets are ICU-version dependent in principle (e.g. `Asia/Calcutta` stays `Asia/Calcutta` in current Node/ICU and *is* in `supportedValuesOf` — verified). Edge risk: a canonical target that is not in the generated list would still preselect Paris; the UTC supplement plus a spot-check assertion over `TIMEZONES` ids vs `resolvedOptions` round-trip in gen-timezones integrity checks would catch any drift at build time.
7. **Out-of-scope neighbors (do not fix opportunistically):** IN-02 (null → Paris), IN-04 (`S.prefs.tz` fallback display), IN-05 (optimistic toast) remain open review items.
