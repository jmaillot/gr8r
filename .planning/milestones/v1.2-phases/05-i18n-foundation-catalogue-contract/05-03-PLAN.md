<objective>
Make the build layout part of the contract: the French catalogue travels as its own chunk, an
English-only build carries none of its bytes, and no catalogue key can add an icon to the bundle.

Purpose: I18N-08 is a property of the shipped artifact, not of the source tree. The English
catalogue is imported statically and the other locales through `import.meta.glob`, so Vite emits
one chunk per locale; a build configured for English only must carry no French string at all. The
plan therefore proves the layout on the REAL bundle, and it names the chunks by an observable
rule — the entry chunk is the asset the built `index.html` loads — so "the French catalogue is not
in the main chunk" is a checkable statement and not a guess. The same plan also proves the
icon-bundle invariant the catalogue format exists to protect: the `lucideSubset()` plugin in
`vite.config.js` reads every quoted lowercase kebab-case token in a `.js` file under `src/` and
pulls the matching Lucide icons into the bundle, so a catalogue authored as `.js` — or a bare-word
key — would silently grow the icon set.

Output: the `localeSubset()` plugin in `vite.config.js`, the `build:en` script, and
`test/build-locales.test.mjs`.
</objective>

  <action>
    **1. Give the build a locale set.** In `vite.config.js`, read the build's locale set from the
    environment at config load time:

    `const BUILD_LOCALES = new Set((process.env.LOCALES || 'en,fr').split(',').map(s => s.trim()).filter(Boolean));`

    The default is `en,fr` — the default build keeps shipping every locale, and no script may
    change that default. `LOCALES=en` is the English-only build.

    **2. Add the `localeSubset()` plugin.** It resolves a locale that is NOT in `BUILD_LOCALES` to
    an empty module, so the locale's strings never reach the bundle:

    - the plugin is named `locale-subset` and is registered with `enforce: 'pre'`, so it sees the
      catalogue import before Vite's own resolver;
    - its `resolveId(source)` matches an import that ends in `locales/<code>.json` — the code is
      captured from the path — and, when that code is not in `BUILD_LOCALES`, returns a virtual id
      of the form `\0virtual:locale-empty:<code>`; for a code that IS in the set it returns `null`
      and the normal resolution continues;
    - its `load(id)` returns the module source `export default {};` for that virtual id, and
      `null` for anything else.

    The empty module is the whole mechanism: the English-only build still resolves the French
    import (the glob in `src/core/i18n.js` still matches it), but the module it resolves to carries
    no French byte. The French chunk may still exist as a near-empty stub — that is expected, and
    the contract is about bytes, not about file names. Do NOT add a second, dynamic import of the
    same catalogue file: importing a file both statically and dynamically makes Vite keep it in the
    entry chunk (D-12).

    **3. Register the plugin.** The plugin list becomes `[lucideSubset(), localeSubset()]`.

    **4. Make the icon scan single-sourced.** `vite.config.js` currently walks `src/` and matches
    the quoted tokens itself (`vite.config.js:12-30`). Replace that inline walk with the shared
    scan plan 05-01 created: import `lucideIconNames` and `lucideIconMarkup` from
    `./scripts/icons.mjs` and build the `ICONS` map from their result — one entry per name, the
    markup from `lucideIconMarkup(name)`. The produced map must be byte-for-byte the same as
    today's — the same set of names, the same SVG markup, the same `export const ICONS = {...};`
    output. The proof is the FROZEN baseline `test/fixtures/icons-baseline.json`, which plan 05-01
    captured from the pre-phase plugin's own output before this file was touched: the new scan
    must reproduce that list exactly. `scripts/icons.mjs` lives outside `src/`, so the scan never
    reads itself and it can never add an icon to the bundle.

    **5. Add the build script.** In `package.json`, add one script next to `build`:
    `"build:en": "LOCALES=en vite build"`. The existing `"build": "vite build"` is unchanged, and
    no `dependencies` block is created (D-14). The project targets Linux and Docker, where the
    `VAR=value command` form is the shell's own. Re-assert the zero-runtime-dependency invariant
    right after this write — the manifest guard of plan 05-02 runs in an earlier wave, so it
    cannot see this file's final state:
    `node -e "const p = require('./package.json'); const d = p.dependencies || {}; console.log('runtime deps:', Object.keys(d).length); if (Object.keys(d).length) process.exit(1);"`

    **6. Do not touch anything else in `vite.config.js`.** The `server.port`, the `server.proxy`
    and the `/api` fallback comment stay exactly as they are.
