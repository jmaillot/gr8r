fields (Accept-Ranges, Content-Range, and the overridable Content-Length) vary.

Range parsing rules (state them in a code comment):
- Read `req.headers.range`. Absent header, or a header that is not a SINGLE
  byte range, is IGNORED — respond 200 with the full body (RFC 7233 allows a
  server to ignore Range). Ignored forms: anything containing a comma
  (multi-range; deliberately NOT implementing multipart/byteranges), a unit
  other than `bytes`, and any malformed shape.
- A valid single range is one of: `bytes=a-b` (0 <= a <= b < size),
  `bytes=a-` (a < size; end = size-1), `bytes=-n` (n > 0; start = size-n,
  clamped to 0, i.e. the last n bytes).
- An UNSATISFIABLE range (start >= size, or a > b when both explicit, or a
  suffix of 0) answers 416 with header `Content-Range: bytes */${stat.size}`
  (plus the nosniff header) and an empty body — no stream is created.
- A satisfied range answers 206 with `Content-Range: bytes ${start}-${end}/${stat.size}`,
  `Content-Length: ${end - start + 1}` (override the full-size default), the
  same D-06 headers (mime, disposition, cache-control, and the inline
  frame-ancestors CSP exactly as today), streams with
  `fs.createReadStream(file, { start, end })` instead of the full-file stream,
  and keeps the existing stream error handling.
- Every response on this function now also carries `Accept-Ranges: bytes`
  (both the 200 and 206 paths) so pdf.js knows ranges are available.
- HEAD keeps its existing contract extended: same status and headers as the
  GET would produce (206 for a satisfied range), body never written.
- `If-Range` is deliberately not honored (one comment line stating it):
  responses are `Cache-Control: private, max-age=3600`, so a stale 206 is a
  bounded, self-healing risk, and pdf.js does not require the validator.

In test/upload.test.mjs, add one integration test next to the byte-only suite
(real-server harness, no mocks — project rule), using `plantFile` with a
known-size buffer (e.g. 100 bytes): assert per the rules above — 200 +
`Accept-Ranges: bytes` + full Content-Length + exact bytes with no Range
header; 206 `bytes=0-9` with Content-Range `bytes 0-9/100`, Content-Length 10
and body equal to the first 10 bytes; 206 `bytes=90-` and 206 `bytes=-10` both
giving the last 10 bytes with Content-Range `bytes 90-99/100`; 416 with
`Content-Range: bytes */100` and empty body for `bytes=100-` and for
`bytes=5-2`; 200 full-body (ignored) for a comma-bearing multi-range
`bytes=0-0,10-20` and a malformed `bytes=abc`; 206 status with empty body for
a ranged HEAD. Keep every existing test passing unchanged.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser navigation → file route | An unauthenticated top-level navigation now receives a 302 instead of 404/401 JSON — the redirect target and its `next` parameter cross back to the client |
| client login → ?next= consumption | A client-supplied query parameter drives a post-login navigation; a hostile value would be an open redirect |
| pdf.js Range requests → byte server | Ranged reads slice the stored file; malformed/hostile range syntax reaches the new parsing path |
