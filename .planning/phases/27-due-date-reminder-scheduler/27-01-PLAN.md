<objective>
Build the server-side reminder scheduler core: a clock-injectable `runReminderPass()` that scans workspaces, computes the workspace-local date/hour from `P.tz`, and for each open reminder window atomically claims a dedup key in a new `reminders_sent` table and appends an in-app notification row via a workspace doc write — then queues reminder emails after commit through the existing pipeline. Idle ticks are pure reads that never bump the workspace revision.

Purpose: This is the engine of the phase — everything Plan 02 adds (settings toggles, inbox rendering) hangs off rows this pass produces.
Output: Working scheduler wired at boot + 1-minute unref'd tick, full window/dedup/gating logic, reminder email fan-out, `test/due-reminders.test.mjs` green for REM-01..REM-05.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler→doc store | The pass writes workspace docs outside the PUT path — must respect revision semantics |
| scheduler→SMTP | Emails leave the trust boundary to external recipients |
| doc data→tz parser | `P.tz` is a stored string consumed by the scheduler — not user-injectable per-request but doc-writable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-01 | DoS | runReminderPass idle tick | high | mitigate | Hour gate (`hour !== 9`) + cheap indexed read before any doc write; idle ticks are pure reads so `revision` never bumps and clients never 409 (REM-01/SC-5); test asserts revision unchanged on off-hour run |
| T-27-02 | Tampering | tz interpretation | medium | mitigate | `TZ_BY_LABEL` literal allow-list of the five settings labels; unknown/empty → UTC fallback; no parsing of `(GMT±..)` out of labels (fixed offsets are DST-wrong); pure localParts tested against DST dates |
| T-27-03 | DoS / Repudiation | dedup + email fan-out | high | mitigate | INSERT OR IGNORE claim inside transaction() BEFORE any doc append — commit-or-neither makes email flooding impossible on retry; duplicate reminder emails structurally impossible per (task, assignee, offset, due) |
| T-27-04 | Information Disclosure | recipient resolution | medium | mitigate | Recipients resolved only for remindable assignees whose project visibility permits (canSee-mirroring remindable predicate); emails ride queueNotifEmails' workspace-scoped authority-row name/email reveal (G-23-1 / T-23-06 precedent) |
| T-27-05 | DoS | interval callback failure | high | mitigate | Whole pass body wrapped in try/catch per workspace + try/catch around the interval callback; async email paths keep their `.catch` → console.warn; an uncaught interval throw would kill the process so this is a hard gate |
| T-27-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this phase (node builtins + node:sqlite only); nothing to gate |
