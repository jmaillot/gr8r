<objective>
Close G-12-1 (PDF iframe refused in Chrome and Firefox) and G-12-2 (the two
« Copier le lien » entry points behave differently and the copied URL renders
nothing top-level) by making `/w/:slug/file/:id` a byte-only route, then fixing
the context-menu copy-link so both entry points resolve the same file URL.

Root causes ( diagnosed in `.planning/debug/pdf-embed-rendering.md` and
`.planning/debug/copy-link-inconsistent-rendering.md`, both confirmed by code
trace):
1. `server.js` routes the file GET by `Accept: text/html` alone — iframe
   navigations send the same Accept as top-level navigations, so the modal's
   iframe got the SPA `index.html` (`X-Frame-Options: DENY`,
   `frame-ancestors 'none'`) instead of the PDF bytes.
2. The « ... » context menu stamps only `data-id` while `A.copyLink` resolves
   file links only from `data-fid`, so the clipboard got the bare workspace
   root; and the pasted path URL bootstrapped the SPA into the modal whose
   iframe hit defect 1 — "url works", bytes never render.

Behavior decision (required by G-12-2's missing item, resolved per the UAT
truth itself): top-level paste serves the bytes directly — inline types render
in the browser tab, attachment types download. This is also the second clause
of D-13 read literally ("the served GET /w/:slug/file/:id route serves real
bytes when opened outside the SPA"). The SPA-side destination stays where it
always was: the in-app preview modal opened via `A.previewFile`. The path-based
SPA bootstrap for files (applyDeepLink 'file') is deleted along with the
server's Accept branch — no code path pretends the SPA owns `/file/:id`.

Purpose: the published file URL becomes honest — every consumer (modal iframe,
fresh paste, old browser) gets the bytes.
Output: byte-only file route, single copy-link URL form, updated e2e + node
integration proofs.
</objective>
