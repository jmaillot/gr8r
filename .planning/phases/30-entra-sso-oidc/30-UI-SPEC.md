# Phase 30 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note (deliberately small):** this phase's UI surface is exactly three things — (1) a conditional "Continue with Microsoft" button on the login card and the join-existing-account card, (2) hiding the password sign-in form under `oidcSsoOnly`, (3) a generic error alert when the OIDC callback fails. No new pages, no new components, no layout changes. Signup/onboarding surfaces are unchanged (D-09).

## Copywriting Contract

All strings catalogued EN + FR in `src/locales/en.json` / `fr.json` (i18n-scan gate applies).

| Element | Copy |
|---------|------|
| Primary CTA | **"Continue with Microsoft"** — reuse existing catalogue key `page.auth.continueMicrosoft` (EN exists; FR copy `fr.json` must stay in parity). Do NOT add a duplicate "Sign in with Microsoft" key. |
| SSO-only subtitle | **"Sign in with your work account."** — new key `page.auth.ssoOnlyHint`; rendered where the password fields were, so SSO-only users understand the card. FR: "Connectez-vous avec votre compte professionnel." |
| Error state (callback failure) | **"Sign-in with Microsoft failed. Try again, or sign in with your password."** — new key `page.auth.ssoError`, rendered in the existing `.alert.danger` slot on the login card (same slot as `e.login`). One generic message for all failure classes (state mismatch, IdP error, denied, account-creation failure) — no failure-detail oracle. FR: "La connexion avec Microsoft a échoué. Réessayez, ou connectez-vous avec votre mot de passe." |
| Error state (SSO-only, password hidden) | Same `page.auth.ssoError` copy minus the password clause — new key `page.auth.ssoErrorOnly`: **"Sign-in with Microsoft failed. Please try again."** FR: "La connexion avec Microsoft a échoué. Veuillez réessayer." |
| Destructive confirmation | None in this phase. |

Rule: the error redirect from `/api/auth/oidc/callback` carries only a generic flag (e.g. `?sso=error`) — never the raw failure reason — and the client maps it to the catalogue string.

## UI Considerations

Applicable state considerations resolved: 5 covered, 1 backstop, 0 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty (feature-off) | SSO button on login + join cards | ✅ covered | When `/api/config` reports `oidcEnabled: false`, the button AND its `.or` divider do not render at all — server ground truth per D-10, never a client env guess |
| hidden-state (SSO-only) | Password form on login card | ✅ covered | When `oidcSsoOnly: true` in `/api/config`, the email/password fields, remember-me, submit button, forgot-password link, and sign-up foot are all hidden; card shows logo, heading, `ssoOnlyHint`, and the Microsoft button |
| error | SSO callback failures | ✅ covered | Callback redirects to `/#login?sso=error`; login card renders `page.auth.ssoError` in the existing `.alert.danger` slot (`role="alert"`) |
| zero-one-many (2FA branch) | Post-SSO navigation | ✅ covered | No new UI: 2FA-enrolled accounts land on the existing `tfaLogin` state (same `{ pending2fa, maskedEmail }` client contract, `src/pages/auth.js` ~line 103); non-2FA accounts land on the app; JIT users land on existing onboarding |
| reuse (button anatomy) | Microsoft button | ✅ covered | Same `btn btn-secondary btn-lg btn-block` classes + inline four-square SVG (14×14) already present in `socialBtns` — visually identical to the existing row, one button, full width |
| state-conflict (demo mode) | `socialBtns` row | 🧪 backstop | Held-out check: with `api.enabled === true` the demo Google/Microsoft/Apple row stays hidden and only the config-gated SSO button may appear; with `api.enabled === false` (prototype mode) the demo row renders and the real SSO button does not — the two never co-render |
