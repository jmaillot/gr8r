<objective>
Build the progress meter of the sweep, then prove it end to end on one literal.

Purpose: the sweep is ~800 user-visible literal occurrences spread over ~50 files. A single task that
sweeps everything is neither executable nor reviewable, and "did we forget a string?" is not a
question a human can answer by reading a diff. This plan builds the device that makes the sweep
mechanical and its completion provable: a static scan of the interface sources, a shrinking
allow-list of the literals that are not extracted yet, and the build gate that turns the scan into
a promise. It then proves the whole pipeline on ONE literal — catalogue, call site, allow-list,
scan, suite — so the later waves are copies of a path that is already known to work.

Output: `scripts/i18n-scan.mjs`, `test/i18n-scan.test.mjs`, `test/fixtures/i18n-pending.json`, the
`i18n:scan` / `prebuild` / `prebuild:en` scripts in `package.json`, and the tracer extraction in
`src/ui/toast.js` + `src/locales/en.json`.
</objective>

  <action>
    Create `scripts/i18n-scan.mjs`. It is plain Node, no dependency, and it lives OUTSIDE `src/`
    for the same reason `scripts/icons.mjs` does: the `lucideSubset()` walk in `vite.config.js`
    reads every `.js` file under `src/`, and a scanner full of English prose would sweep its own
    pattern strings into the icon bundle and change the frozen 174-name baseline.

    The module exports:

    - `scanTree(root = 'src')` → an array of findings `{ file, line, kind, text }`, one per
      detected occurrence. `file` is the path relative to the repository root, `kind` is the rule
      family that caught it, `text` is the decoded literal.
    - `scanSource(text, file)` → the same array for one file's content, so a test can scan a
      string without touching the disk.
    - `EXCLUDED_FILES` → the set of files never scanned. It holds `src/data/seed.js` (demo
      content) and nothing else.
    - `main()` → the CLI. It reads the allow-list, compares it with the findings and exits 1 on a
      violation. `--report` prints every finding with its file and line instead.

    The rule families, each one a named function so a finding names the rule that caught it:

    1. `ruleTextNode` — an HTML text node: the content between `>` and `<` inside a template
       string, trimmed, reported when it holds at least two letters and is not a pure
       interpolation, a symbol or an entity.
    2. `ruleAttribute` — the value of `aria-label`, `placeholder`, `title`, `alt` and `data-tip`,
       reported when it holds at least two letters and is not a pure interpolation. The `value`
       attribute is deliberately NOT in this family: a literal `value` is a form or machine value
       (`value="list"`, `value="board"`, `value="all"`, `value="__remove"`), and the dynamic ones
       are interpolations, which the rule skips anyway.
    3. `ruleToast` — the first argument of a `toast(...)` call, and the message argument of
       `mutate(...)`.
    4. `ruleHelperArgument` — the arguments of the documented display helpers: `empty` (its
       second and third arguments), `H`, `srow` (its first and second), `I` (its third), `tog`,
       `card`, `sk`, `miniRow`, `actHtml`, `kcard`, `pageTitle`. The helper list is a named
       constant in the module, with a comment saying that a helper added to the interface must
       be added to that list.
    5. `ruleDisplayName` — the value of an object property named `name`, `label`, `title`, `desc`,
       `text`, `hint` or `message`; plus every value of an object assigned to a const whose name
       ends in `NAMES`, `LABELS`, `TITLES` or `HEADINGS` (the display tables: `ROUTE_NAMES`,
       `ROLE_LABELS`, `STATUSES`, `PRIOS`, `LABELS`, `PSTAT`).
    6. `ruleProse` — a free-standing string literal that contains a space and begins with a
       capital letter. This is the catch-all for the labels that reach the interface through a
       helper nobody documented.
    7. `ruleDisplayLabel` — **a single-word capitalised display label**. A *display label* is a
       quoted literal whose shape is `^[A-Z][A-Za-z0-9]{2,}$` — an initial capital, no space, no
       punctuation — that sits in a DISPLAY position. The display positions are:

       - **D1 — a tuple label**: the second element of a two-element array literal whose first
         element is a machine key (`['manual', 'Manual']`, `['priority', 'Priority']`). The first
         element is the machine key and is never reported.
       - **D2 — a display table**: an element of a flat array literal assigned to a const (the
         `stN` state names of the design-system page, the `PERMS` permission names).
       - **D3 — a display-named property**: the value of an object property whose name is `name`,
         `label`, `title`, `desc`, `text`, `hint`, `message`, `n` (the file-type table's display
         name) or `action` (the toast options' action-button label).
       - **D4 — a fallback**: the right-hand side of a `||` whose left-hand side is a member
         expression, a call or an attribute read (`ROLE_LABELS[role] || 'Member'`,
         `… || 'Choose'`).
       - **D5 — a returned label**: a capitalised single word in a `return` statement.

       The rule is a POSITION rule, not a lexical one: the same word is a display label in one
       position and a machine identifier in another. `'Member'` is the display fallback of
       `roleLabel()` and the display name of the role table (reported), and a stored role id in
       the `ROLES` table and in a comparison (not reported).

    The exclusions, each one a named function or set, applied before a finding is reported:

    - `isMachineIdentifier(text, context)` — the syntactic contexts: a comparison operand, a
      switch case, an object key, a `data-*` / `id` / `class` / `style` / `href` / `src` / `type` /
      `role` / `rel` / `tabindex` attribute value, an `ic('…')` argument, an element name, a CSS
      declaration value, a CSS custom property (`--bg`), an import specifier, a path, a URL, a
      number, a date, a duration, a regex and a lowercase kebab-case token (the icon scan's
      vocabulary).
    - `MACHINE_SETS` — the machine values that are capitalised and single-word, one named set per
      CATEGORY, each entry carrying a comment saying why the value is a machine identifier and
      where it is used:

      | Set | Values | Why it is machine |
      |-----|--------|-------------------|
      | `HTTP_VERBS` | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | the REST verbs `src/core/api.js` passes to `call()` |
      | `KEYBOARD_KEYS` | `Enter`, `Escape`, `Esc`, `Tab`, `Backspace`, `Del`, `ArrowUp`, `ArrowDown` | the key names the keyboard map matches on |
      | `ROLE_IDS` | `Owner`, `Admin`, `Member`, `Guest` | the role values the DOCUMENT stores (`src/core/constants.js:64`, `src/core/store.js:250-251`); the display of a role is a catalogue lookup, the id never changes |
      | `MONTH_WEEKDAY_NAMES` | `Jan`…`Dec`, `January`…`December`, `Sun`…`Sat`, `Sunday`…`Saturday` | the four English date arrays of `src/core/utils.js:40-43`, which plan 06-04 deletes |

      A set that accumulates one entry per finding is a disguised allow-list and must not be
      created: a value that belongs to no category is a missing RULE, and the rule is written
      (the calibration of Task 2 enforces this).
    - `STORED_VALUES` — the stored preference values the application displays verbatim:
      `'(GMT-08:00) Pacific Time'`, `'(GMT-05:00) Eastern Time'`, `'(GMT+00:00) London'`,
      `'(GMT+01:00) Berlin'`, `'(GMT+08:00) Singapore'`, `'(GMT-07:00) Pacific Time'`,
      `'English (US)'`, `'English (UK)'`, `'Deutsch'`, `'Español'`, `'Français'`, `'日本語'`,
      and the four stored date patterns `'MMM d'`, `'d/M'`, `'M/d'`, `'yyyy-MM-dd'`. Every entry
      carries a comment saying it is a stored value, not interface text, and that phase 8
      (LOC-02, LOC-04) replaces the language list.
    - `DEMO_VALUES` — the demo content values that live outside `src/data/seed.js` and are shown
      to the user as stored data: the default member name, the default project name, the default
      workspace name. Each entry carries a comment naming why it is data.
    - a dotted catalogue key (`^[a-z][a-z0-9]*(\.[a-z][a-zA-Z0-9]*)+$`) is a lookup, never prose.

    The CLI compares the findings with the allow-list and reports three kinds of violation:

    - `pending` — a finding that the allow-list covers: acceptable during the sweep, and the
      reason the sweep is not finished yet.
    - `unlisted` — a finding the allow-list does NOT cover: a literal that was never put in a
      catalogue. This is the violation that fails the build (success criterion 1).
    - `stale` — an allow-list entry whose literal is no longer detected: the entry must be
      removed, because the list is a meter and a meter that keeps dead entries is not a meter.

    **The second check family — the catalogue keys.** The scan also resolves the keys the
    sources ask for, because `t()` returns the key ITSELF when it cannot resolve it
    (`src/core/i18n.js:114-124`): a literal traded for a raw key renders `toast.doesNotExist` in
    the interface, and no other test in the tree would ever notice. The scan therefore reads
    `src/locales/en.json` and, for every literal key of a `t('…')` call site under `src/`,
    reports two more kinds of violation:

    - `unresolved` — the key is not a key of the English catalogue.
    - `placeholder-mismatch` — the vars passed at the call site do not match the placeholders of
      the catalogue value: the value's placeholder set must equal the call site's var names, so a
      value that interpolates `{title}` is never called with `{name}`.

    The key family reads the CATALOGUE, never the DOM: the English catalogue is the base every
    locale falls back to (`src/core/i18n.js:115-120`), so a key that exists in `en.json` resolves
    in every locale. A dynamic key (`t('nav.route.' + id)`) is not a literal key and is not
    checked here; the coverage of the dynamic keys is proved by the vocabulary tests of plan
    06-08.

    Exit 1 when there is at least one `unlisted`, `stale`, `unresolved` or `placeholder-mismatch`
    violation; print the file, the line and the literal of every violation so the message is
    actionable. Exit 0 when every finding is covered, no entry is stale and every literal key
    resolves.

    Create `test/i18n-scan.test.mjs` with `node:test` and `node:assert/strict`. It must NOT
    depend on the live tree, because the live tree changes in every later wave: it writes a small
    fixture tree under `os.tmpdir()` (a couple of `.js` files with a text node, an attribute, a

    the rules one by one. The suite also asserts the three CLI verdicts: a finding covered by the
    allow-list is accepted, an unlisted finding is a violation, and a stale entry is a violation.

    **The real instances.** The suite carries a `REAL_INSTANCES` table: a list of `{ file, line,
    snippet, expected }` entries whose `snippet` is the VERBATIM source excerpt copied from the
    real file, and whose `expected` is the label the scan must report. The excerpts are the
    measured instances of the display-label class:

    | File | Line | The instance | The label expected |

    | `src/overlays/popovers.js` | 280-288 | the sort table `['manual', 'Manual'], ['priority', 'Priority'], …` | `Manual`, `Priority`, `Title`, `Status`, `Assignee`, `Created` |
    | `src/main.js` | 78, 85 | the toast options `action: 'Reload'` and `action: 'Retry'` | `Reload`, `Retry` |
    | `src/ui/select.js` | 21 | the `aria-label` fallback `|| 'Choose'` | `Choose` |
    | `src/core/store.js` | 251 | the role fallback `|| 'Member'` | `Member` |
    | `src/ui/helpers.js` | 74-83 | the file-type table's `n: 'Figma'` | `Figma` |

    Each excerpt is scanned with `scanSource(snippet, file)` and the scan must report exactly the
    expected labels — no more, no fewer. A second table, `MACHINE_INSTANCES`, carries the
    excerpts that must report NOTHING: a `data-a="setSort"` attribute, a `data-r="home"` route, a
    `data-v="1"` value, a `class="mi"` value, an `import { x } from '../core/utils.js'` specifier,
    a `call('GET', '/api/config')` verb, a `['Owner', 'Admin'].includes(role)` comparison, a
    keyboard key name and a `class="tab-btn"` CSS-ish token.

    **The machine-identifier guard.** One test scans the LIVE tree and asserts that no finding
    sits at a `data-a`, `data-r` or `data-v` site: the scanner reads every `data-*` attribute
    value of every `.js` file under `src/` (438 `data-a`, 58 `data-r`, 76 `data-v` are measured)
    and asserts that none of them is a reported finding. This test is the guard the calibration
    needs: the moment a rule grows broad enough to catch a machine identifier, it fails.

    **The key-resolution assertions.** The suite asserts that a `t('a11y.doesNotExist')` call
    site is an `unresolved` violation, that a `t('a11y.dismiss')` call site with a var the value
    does not carry is a `placeholder-mismatch` violation, and that a dynamic key
    (`t('nav.route.' + id)`) is not reported.
