<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/auth/tfa/factors/{enroll,enable,remove} | authenticated user; body fields (label, codes, factorId) are untrusted |
| untrusted 6-digit codes → factor loop | brute-force surface scales with factor count if attempts semantics drift |
| remove route → disable transaction | wrong branch selection could leave two_fa_enabled=1 with zero factors |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-06 | Spoofing | add-factor enroll gate | high | mitigate | TOTP2-05/D-04: live code from an existing factor verified server-side before the new QR/secret is stashed or returned; password step-up on the same request |
| T-31-07 | Spoofing | factor verify loop (N factors) | medium | mitigate | D-11: attempts increment precedes comparison; one attempt per submission regardless of N; per-route `tooMany` bands; no per-factor attempt writes |
| T-31-08 | DoS | remove route | high | mitigate | D-15: code must verify against a factor that is NOT the target — self-lockout structurally impossible; D-18 delegation keeps the disable contract (recovery wipe + session revoke) for the last factor |
| T-31-09 | Elevation of Privilege | recovery vs TOTP boundary | medium | mitigate | Strict 6-digit gate with no recovery lookup in any new route (D-14/D-59/D-72); recovery branch stays outside the factor loop |
| T-31-10 | Tampering | label storage | low | mitigate | Trim + length-validate at enroll (D-02); stored as data, rendered client-side via `t()`/`esc()` only (Plan 03); never interpolated into SQL (parameterized statements throughout) |
| T-31-11 | Information Disclosure | staged pending secrets | medium | mitigate | D-13: staging rides the existing in-memory 10-min TTL pending map (D-46 invariant) — never persisted; per-factor key extension only |
</threat_model>
