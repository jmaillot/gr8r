## Summary

Everything this phase needs already has an in-repo precedent. The doc-PUT transaction (server.js:5901-5963) already demonstrates the exact collect-in-tx / fire-after-commit shape WHK-02 requires: `newNotifs` is diffed against the stored doc inside the tx, then email and push fan-outs run post-commit fire-and-forget ("the response must never wait on SMTP"). `diffWebhookEvents(storedDoc, next)` is a pure sibling of the existing `logDocChanges` diff logic (task added/removed/assigned/completed/commented) — the 8-event vocabulary maps almost 1:1 onto diffs already computed there. `due.reminder` is the one event that does NOT come from the doc-PUT diff: it originates from the reminder funnel (runReminderPass tick), so the emission point must accept events from two sources.

Exactly-once delivery rides the `reminders_sent` claim pattern (server.js:382-391): a claim row inserted inside the same transaction that enqueues the delivery (INSERT OR IGNORE / ON CONFLICT DO NOTHING), never mark-then-send. The retry driver should follow the runReminderPass shape: a `.unref()`'d setInterval pass (server.js:7825-7832) that drains due deliveries with try/catch + promise catch (an uncaught throw in a setInterval callback kills the process — house rule documented at the site). SSRF guard is a new pure module checked at every delivery attempt: parse URL (https-only, host must end `.logic.azure.com` is NOT sufficient — the requirement says targeting `*.logic.azure.com` but validation should be https + resolved-IP deny-list; re-resolve DNS per attempt to defeat DNS-rebinding between registration and delivery).

Zero new dependencies is enforced (REQUIREMENTS.md): HMAC via node:crypto (`createHmac('sha256', secret)`), DNS via node:dns/promises `lookup`, HTTP via global fetch with `AbortSignal.timeout()` (oidc.js:127 house rule, 10 s).

**Primary recommendation:** 4 artifacts — (1) pure `src/core/webhook-events.js` (diff + per-event whitelist envelope builders, zero imports); (2) server `webhookHooks` module (mirror tables, CRUD routes, delivery engine + claim table + retry pass + SSRF guard); (3) formatter module (3 formats, pure, unit-testable); (4) projectSettings "Webhooks" section in a lazy chunk with EN+FR keys.

### Anti-Patterns to Avoid
- **Mark-then-send:** never set a "sent" flag before the HTTP call (Phase 38 no-double-send invariant; STATE.md:64). Claim first (INSERT OR IGNORE), send after.
- **Emitting events from the client or MCP path:** events derive ONLY from the server-side funnel diff. MCP writeDoc rides mergeClientDoc (mcp.js:32-35), so MCP-authored changes naturally produce events — that is correct and free; a separate MCP webhook-management route is explicitly out of scope.
- **Resolving DNS at registration only:** DNS rebinding between registration and delivery defeats a registration-time check. Resolve per attempt (WHK-05).
- **Blocking the PUT on delivery:** any `await deliver()` inside the tx or before the response — hanging endpoint delays the PUT. Fire-and-forget only.
- **Putting hook config in the doc:** mirror tables only; a doc-carried `webhooks[]` would leak URLs/secrets to every client via docForClient.

## Common Pitfalls

### Pitfall 1: Diff point reads normalized vs raw docs inconsistently
**What goes wrong:** `diffWebhookEvents(storedDoc, next)` fires spurious task.assigned/task.completed events because one side was normalized (assignees scalar vs array, done as string) and the other wasn't.
**Why:** mergeClientDoc normalizes the incoming doc; storedDoc is raw JSON from disk.
**How to avoid:** run the diff AFTER `docFromClient` returns `next` (both sides then in canonical shape — `normalizeProjects(stored)` already runs inside mergeClientDoc:1293). Reuse the exact Map-building approach of logDocChanges (server.js:2360-2377) so the diff sees the same shapes.
**Warning signs:** duplicate events after a no-change save.

### Pitfall 2: One event per write, not per assignee
**What goes wrong:** a task assigned to 3 people fires 3 task.assigned events per hook.
**How to avoid:** one delivery per (hook, event, taskId); the event payload carries the assignee list; the Teams formatter renders the mention(s).

### Pitfall 3: Forgetting due.reminder's second emission source
**What goes wrong:** the pure diff at the doc-PUT only covers 7 of 8 events; due.reminder originates in the reminder funnel (runReminderPass) — if only the funnel diff emits, due.reminder never fires.
**How to avoid:** emission function takes (workspaceId, event, payload) and is called from BOTH sites; the reminder site must reuse the reminders_sent-style dedup so reminder + webhook claim don't double-fire.

### Pitfall 4: 28 KB measured wrong
**What goes wrong:** cap measured on the inner card, not the full JSON body (Teams cap applies to the message payload the workflow posts).
**How to avoid:** measure `Buffer.byteLength(JSON.stringify(fullPayload))` after formatting; truncate the whitelisted "biggest field" (D-02: notes/comment body) in the ENVELOPE, re-measure after formatting, then send.
**Warning signs:** Workflows 400s on large comment.added events.

### Pitfall 5: SSRF guard missing redirect handling or IPv6
**What goes wrong:** fetch follows a redirect to an internal address, or the deny-list only covers IPv4.
**How to avoid:** deny-list check must cover IPv6 loopback (::1), link-local (fe80::/10), and unique-local (fc00::/7) alongside loopback/127.0.0.0/8, RFC1918 (10/8, 172.16/12, 192.168/16), 169.254.0.0/16 [WHK-05 names the IPv4 set; IPv6 coverage is standard hardening]. Disable or validate redirects (fetch `redirect: 'manual'` then re-guard, or `redirect: 'error'` — Workflows URLs don't redirect in practice).

### Pitfall 6: Secret leaks into logs or client doc
**What goes wrong:** a log line prints the hook row, or docForClient/projects serialization picks up the table.
**How to avoid:** hooks never enter the doc; log only hook id + delivery id + status codes, never URL query (the Workflows URL itself IS a bearer secret — log host only) and never the signing secret.

### Pitfall 7: Retry-After in seconds vs HTTP-date
**What goes wrong:** `Number(header)` NaN on an HTTP-date Retry-After → NaN next-attempt timestamp → delivery stuck.
**How to avoid:** parse both forms; fall back to the D-05 backoff table when absent/unparseable.

### SSRF guard skeleton
```js
import dns from 'node:dns/promises';
import net from 'node:net';
const DENY = ip => {
  if (net.isIPv4(ip)) {
    const [a, b] = ip.split('.').map(Number);
    return a === 127 || a === 10 || (a === 172 && b >= 16 && b <= 31) ||
           (a === 192 && b === 168) || (a === 169 && b === 254) || a === 0;
  }
  return /^(::1|f[cd]|fe[89ab])/i.test(ip) || ip === '::';
};
async function ssrfOk(urlStr) {
  const u = new URL(urlStr);
  if (u.protocol !== 'https:') return false;
  const { address } = await dns.lookup(u.hostname, { all: false, verbatim: true });
  return !DENY(address); // multi-IP hosts: lookup({all:true}) and require every IP clean
}
// call per attempt, BEFORE fetch; fetch(..., { redirect: 'error' })
```
